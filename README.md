# four-keys-metrics-viewer

Four Keys（デプロイ頻度・変更のリードタイム・変更障害率・サービス復元時間）を
可視化するためのリポジトリです。

---

## コンセプト

> 本セクションは要件定義前のコンセプト（方向性）の記述です。詳細仕様は別途定義します。

### このアプリケーションが目指すもの

GitHub 上の活動履歴から **DORA のソフトウェアデリバリーパフォーマンス指標** を自動で算出し、
チームが「自分たちの開発プロセスの現在地」を対話のきっかけとして眺められる Web アプリケーションを作ります。

DORA 公式ガイドが指摘するとおり、これらの指標は
「組織パフォーマンスと開発者のウェルビーイングの *先行指標*」であり、
「ソフトウェア開発・デリバリープラクティスの *遅行指標*」です。
本アプリは**評価のための計測ツールではなく、改善のための会話を生む可視化ツール**という立場を取ります。

### 対象とする指標（5指標 / 2つの因子）

DORA は現在、指標を **スループット（Throughput）** と **不安定性（Instability）** の
2つの因子に分けた 5 指標で定義しています。

#### スループット — 変更がシステムをどれだけ流れるか

| 指標 | 定義 |
| --- | --- |
| 変更のリードタイム<br>(Change lead time) | コードがバージョン管理にコミットされてから本番にデプロイされるまでの時間 |
| デプロイ頻度<br>(Deployment frequency) | 一定期間内のデプロイ回数、またはデプロイ間隔 |
| 障害デプロイ復旧時間<br>(Failed deployment recovery time) | 即時対応を要する失敗デプロイから復旧するまでの時間 |

#### 不安定性 — デプロイがどれだけうまくいくか

| 指標 | 定義 |
| --- | --- |
| 変更失敗率<br>(Change fail rate) | デプロイのうち、ロールバックやホットフィックスなど即時対応を要した割合 |
| デプロイ手戻り率<br>(Deployment rework rate) | 本番障害に起因して発生した、計画外デプロイの割合 |

### 指標の変遷を踏まえる

リポジトリ名の由来である従来の "Four Keys" から、指標は次のように更新されています。
本アプリは**最新の 5 指標モデルに準拠**しつつ、過去データとの継続性にも配慮します。

- **2014〜**: 4 指標。安定性の指標として MTTR（平均修復時間 / Time to restore service）を採用。
- **2023**: MTTR を **障害デプロイ復旧時間（Failed deployment recovery time）** に改称・再定義。
  従来の定義では「ソフトウェア変更に起因する障害」と「データセンター障害など外部要因の障害」を
  区別できていなかったため、**本番への変更が引き起こしたサービス低下からの復旧**に対象を絞り込んだ。
  これにより他のデリバリー指標との統計的な整合性も向上した。
- **2024**: 5 つ目の指標として **デプロイ手戻り率（Deployment rework rate）** を追加。
  変更失敗率が実質的に「手戻り量の代理指標」として機能していたことが判明したため、
  手戻りを直接測る指標を新設。同時に指標体系を「スループット / 不安定性」の 2 因子構造へ再編した。

### 基本コンセプト

1. **GitHub をデータソースにする**
   専用のエージェント導入や既存 CI/CD パイプラインの改修を前提とせず、
   GitHub に既にあるデータ（コミット、Pull Request、Deployments、Releases、Actions の実行履歴、
   Issue のラベル等）から可能な範囲で指標を導出します。
   「完璧な計測のための投資より、まず会話を始めること」という DORA の示唆に沿った軽量な導入を優先します。

2. **アプリケーション / サービス単位で見る**
   DORA は指標を「1つのアプリケーションまたはサービス単位」で適用することを推奨しています。
   本アプリもリポジトリ（あるいはリポジトリ内のサービス単位）をスコープの基本単位とし、
   組織横断での安易な合算・比較は行いません。

3. **推移を見る（点ではなく線）**
   単発のスナップショットではなく時系列での変化を主役に据え、
   施策の前後で何が動いたのかを読み取れるようにします。
   スループットと不安定性を並べて表示し、「速度と安定性はトレードオフではない」ことを確認できる形にします。

4. **算出ロジックを開示する**
   何をデプロイとみなすか、何を障害とみなすかは組織ごとに異なります。
   指標の定義とマッピングルールを設定可能にし、
   画面上でも「この数値がどう計算されたか」を辿れるようにします。

5. **Quick Check 相当のセルフチェックを併設する**
   自動計測が難しい指標（障害の定義に依存するものなど）を補うため、
   DORA Quick Check と同等の 5 つの設問によるセルフ評価と、
   自動算出値との突き合わせを行えるようにします。

### 意図的に避けること（アンチパターン）

DORA 公式が挙げる落とし穴を、プロダクトとして踏まないための方針です。

- **個人の評価に使わせない** — 個人単位のランキングやスコアリングは提供しません。
- **目標値を押し付けない** — 「全アプリが 1 日複数回デプロイ」のような一律の目標設定は
  ゲーミングを招くため、アプリ側からの固定目標の提示は行いません。
- **単一スコアに丸めない** — 5 指標を 1 つの総合点に潰して優劣を語る見せ方は主目的にしません。
- **チーム間の競争を煽らない** — 比較の軸は「他チーム」ではなく「過去の自分たち」に置きます。
