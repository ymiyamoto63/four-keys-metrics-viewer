# サンプルリポジトリ: 作り方と E2E 確認手順

対象は 2 つ。**サンプルリポジトリ `four-keys-sample-service` を作ること**（#22）と、
**それを使って収集から表示までを確認すること**（#23）。ADR-0004「検証方法」で決めた
構成を前提にした手順であり、`README.md` の「動かし方」を一度通してあることを前提にする。

> **前提**: サンプルリポジトリの用途は **E2E（GitHub API のレスポンス形が想定どおりかの確認）に
> 限定する**（ADR-0004）。指標計算の正しさは fixture ベースのユニットテスト（#16）と
> `src/sample-repo/plan.test.ts` が担保しており、**この手順で指標の正しさを検証しようとしない**。
> ここで分かるのは「実際の GitHub からの収集が通るか」だけである。

---

## 0. なぜ合成履歴と本物の CD の両方が要るか

GitHub のタイムスタンプには、過去日付で作れるものと作れないものがある。

| データ | 過去日付で作れるか |
| --- | --- |
| コミット / マージコミットの committer date | **作れる**（git オブジェクトの一部） |
| PR の `created_at` / `merged_at` | 作れない |
| Actions の実行日時 | 作れない |
| Deployments / Releases の日時 | 作れない |

したがって **合成履歴だけでは `workflow_run` ルール（#14）を検証できず、
本物の CD だけでは 1 年分の推移を検証できない。** 片方では MVP の 2 戦略の半分しか
検証できない（ADR-0004 / ADR-0001）。

生成物の内訳もこの表に対応している。

- **合成履歴**（`src/sample-repo/plan.ts` + `generate.ts`）が `default_branch` ルールを検証する
- **本物の CD**（`.github/workflows/deploy.yml`）が `workflow_run` ルールを検証する

## 1. 合成履歴を生成する

生成はローカルで完結する。**GitHub には何も作らない。**

```sh
npm run sample:generate -- --out ../four-keys-sample-service
```

出力先は空ディレクトリ（または存在しないパス）でなければならない。既存の履歴の上に
数百コミットを重ねると、どこまでが生成物か分からなくなるため、空でなければ中断する。

主なオプション（すべて省略可能）。

| オプション | 既定 | 用途 |
| --- | --- | --- |
| `--out` | （必須） | 生成先ディレクトリ |
| `--now` | 現在時刻 | 基準時刻。この時刻が属する週が最新の週になる |
| `--weeks` | 53 | 何週分作るか。既定はバックフィル既定の 365 日を覆う長さ |
| `--seed` | 20260920 | 乱数の種。**同じ `--now` と `--seed` なら必ず同じ計画になる** |
| `--branch` | `main` | デフォルトブランチ名 |

完了すると、積んだコミット数・デプロイ数と、**意図的に仕込んだ異常ケースが
どの週に入ったか**がログに出る。この一覧は後の「4. 画面で確認する」でそのまま使うので控えておく。

### 何が入るか

`plan.ts` の `ANOMALIES` が正であり、`plan.test.ts` が「本当に入っているか」を検証している。
既定（53 週・既定シード）では **590 コミット / 186 デプロイ / 54 週**になる。

| 異常ケース | 何を確認するためか |
| --- | --- |
| デプロイが 1 件も無い週（4 回。うち 2 週は連続） | 線が途切れること。**「0 件」と「データなし」を書き分けること** |
| （直接 push だけの週を足して、デプロイ 0 件の週は計 5 回） | コミットはあるがデプロイが無い週の表示 |
| デプロイが 1 件だけの週（2 回） | デプロイ間隔の中央値を出さない条件（標本 < 3 件） |
| 7 週間 / 12 週間放置された branch の merge | リードタイムの外れ値。p90 と裾が潰れないこと |
| （上記の放置ブランチはコミットを 4〜6 件積む） | 外れ値 1 件では p90（上位 10%）に届かず**代表値に現れない**ため |
| 同一時刻の 2 件 / 3 件のデプロイ | 二重計上が起きないこと。デプロイ間隔 0 時間 |
| PR を経由しない直接 push（単独の週と、merge と混ざる週） | コミット単位のリードタイムが取りこぼさないこと |

**異常ケースは最古の週と最新の週には置いていない。** どちらも収集カバレッジが必ず
`partial` になり（バックフィルの端と進行中の今週）、デプロイ回数が `null` で表示されるため、
そこに欠損週を置いても「意図した 0」なのか「まだ集めていない」のか区別が付かない。

## 2. GitHub にリポジトリを作って push する

**ここから先は外向きの操作で、このリポジトリのスクリプトは一切自動化しない。**
生成をやり直せることのほうが、ここを自動化して省ける手間より価値が大きい。

```sh
cd ../four-keys-sample-service

# 1. リポジトリを作る。private でよい（PAT は private も読める）。
gh repo create four-keys-sample-service --private --source=. --remote=origin

# 2. 合成履歴ごと push する
git push -u origin main
```

### 2.1 CD を緑にする

`deploy.yml` は main への push で走り、**GitHub Pages へ実際にデプロイする**。
`configure-pages` に `enablement: true` を付けてあるので通常は自動で有効化されるが、
組織のポリシーなどで有効化できない場合は手動で設定する。

- `Settings` → `Pages` → `Build and deployment` → `Source` を **GitHub Actions** にする

```sh
gh run list --workflow deploy.yml
```

**`conclusion` が `success` の実行が 1 件以上あることを確認する。**
`workflow_run` ルールは成功実行だけをデプロイとして数えるため（`src/deploy/workflow-run.ts` の
`isDeployRun`）、ここが赤いままだと #23 の `workflow_run` 側が**デプロイ 0 件**になる。
そして症状は「グラフが空」なので、**収集側のバグと区別が付かない。** 先に緑にしておくこと。

### 2.2 実データを積む

合成履歴には PR が 1 件も無い（PR の `created_at` / `merged_at` は過去日付で作れないため、
合成履歴側は merge commit だけで構成してある）。**リードタイムの 3 区間内訳**
（「コミット → PR open」「PR open → merge」「merge → デプロイ」・ADR-0004）は
PR が無いと出ないので、以後は実際に PR を作って merge し、実データを積む。

```sh
git switch -c feature/first-real-change
echo "// 最初の実 PR" >> features/real-0001.js
git add -A && git commit -m "feat: 最初の実 PR"
git push -u origin feature/first-real-change
gh pr create --fill && gh pr merge --merge --delete-branch
```

`--merge`（マージコミットを作る）を使うこと。squash / rebase は merge commit を残さないので、
`merge_only` 粒度ではデプロイとして検出されない。

### 2.3 作り直すときの注意

合成履歴を生成し直すと**別のコミット SHA になる**。push は force push になり、
収集済みのデータとは結び付かなくなる。作り直したら**収集側の DB も作り直す**こと
（`docs/operations.md`「3.3 復旧手順」の要領で、空の volume から始める）。

## 3. スコープとして登録する

#23 は **2 つのスコープ設定**で確認する。`scopes.toml` に両方書くと 1 回の収集で
両方見られるが、**同じリポジトリを 2 つのスコープとして登録することになる**点に注意する。
これは ADR-0001 が禁じた「1 スコープに 2 ルールの OR 合成」には当たらない
（スコープが別なので合算も横並び比較もされない）。

```toml
# 合成履歴の 1 年分を見る。
[[scopes]]
id = "sample-default-branch"
owner = "<your-account>"
repo = "four-keys-sample-service"
backfill_days = 365

[scopes.deploy_rule.default_branch]
granularity = "merge_only"

# 本物の CD の成功実行を見る。
[[scopes]]
id = "sample-workflow-run"
owner = "<your-account>"
repo = "four-keys-sample-service"
backfill_days = 365

[scopes.deploy_rule.workflow_run]
workflow = "deploy.yml"
```

PAT の **Repository access** にこのリポジトリを追加するのを忘れないこと
（`docs/operations.md`「1.1 発行手順」手順 5）。追加し忘れると 403 になり、
収集はエラーとして記録されるがプロセスは落ちない。

反映後、起動して収集を待つ。

```sh
docker compose down && docker compose up -d
```

## 4. 画面で確認する（#23 の完了条件）

`http://127.0.0.1:3000/` を開き、スコープを切り替えながら確認する。
**すべてにチェックが付いて初めて #23 を閉じられる。**

### 4.1 収集が完走すること

- [ ] サマリ画面に**最終収集成功時刻**が出ており、現在から 1〜2 時間以内である（#20）
- [ ] **バックフィル進捗**が完了を示している（#20）。完走まで数分かかることがある
- [ ] 2 つのスコープの両方でエラーが出ていない（片方の失敗はスコープ単位で吸収されるため、
      画面を見ないと気付けない）

### 4.2 `sample-default-branch`（合成履歴）

- [ ] **1 年分（54 週）のチャートが描かれている。** 右端が現在週
- [ ] デプロイ頻度が週ごとに上下している（定数線になっていない = 推移が見える）
- [ ] **「1」で控えた欠損週でデプロイ回数が 0 と表示され、線が繋がっていない**（#19）。
      既定シードなら該当は 5 週（うち 1 週は直接 push だけの週）。
      「データなし」ではなく **0 件**と読めること。両者の書き分けが #17 の核心
- [ ] 欠損週が 2 週続く区間でも、間を補間した線が引かれていない
- [ ] デプロイ 1 件だけの週（既定シードで 2 週）で、**デプロイ間隔の中央値が表示されない**
      （標本 < 3 件）。回数の「1 回」のほうは表示される（ゲートは副指標だけに掛かる）
- [ ] 同一時刻に複数デプロイを置いた週（2 件の週と 3 件の週が 1 つずつ）で、回数が
      その件数どおりになっている（二重計上が無い）。デプロイ間隔に 0 時間が立つ
- [ ] リードタイムのチャートで、放置ブランチを merge した週に**外れ値が見える**。
      既定シードなら **p90 が約 59 日と約 33 日の週が 1 つずつ**あり、平常週の p90（約 2 日）の
      桁を超える。**そのときも中央値は 2 日以下に留まる**——中央値が一緒に跳ねていたら、
      外れ値が「たまたま全体が遅かった週」に見えてしまい、p75 / p90 を重ねた意味が無くなる
      （ADR-0004「中央値だけだと一番会話すべき事実が消える」）
- [ ] 指標詳細画面（#21）で、外れ値の週をドリルダウンすると**放置ブランチのコミット**が
      リードタイムの長い順に並ぶ
- [ ] 直接 push だけの週の commit が、**次のデプロイの差分に含まれている**
      （PR を経由しないコミットを取りこぼしていないこと）
- [ ] 最古の週と最新の週が **`partial`（収集中 / データなし）**として表示されている

### 4.3 `sample-workflow-run`（本物の CD）

- [ ] **CD の成功実行がデプロイとして数えられている。** 件数が
      `gh run list --workflow deploy.yml --json conclusion --jq '[.[]|select(.conclusion=="success")]|length'`
      と一致する
- [ ] 失敗・キャンセルした実行が数えられていない
- [ ] 過去の週は**すべてデプロイ 0 件**である（Actions の実行日時は過去日付で作れないため、
      実行は今週以降にしか存在しない）。**これは不具合ではない**——そしてこれが
      「本物の CD だけでは 1 年分の推移を検証できない」の実物である
- [ ] 画面に出ている検出ルールが `workflow_run:deploy.yml` である（柱 4）

### 4.4 レスポンス形の確認（この手順の本来の目的）

- [ ] 収集ログに射影の失敗（`parents` が読めない等）が出ていない
- [ ] 実データの PR を merge した週で、リードタイムの**3 区間内訳**が表示される（#21）。
      合成履歴の週では PR が無いので内訳が出ない——**この差が出ることまで含めて期待どおり**
