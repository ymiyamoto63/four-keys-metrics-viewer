# Spike 0025: D1 の容量・書き込み制限の見積もり

- 日付: 2026-09-20
- 対象 Issue: #25
- 関連 ADR: ADR-0002, ADR-0003

## 結論

**D1 の容量・書き込み制限は本アプリの想定規模では一切ボトルネックにならない。**
一方で調査の過程で、**ADR-0003 に事実誤認があった**ことが判明した。

> ADR-0003 の記述: 「Cron Triggers と D1 が標準装備で、**無料枠で常時稼働でき**」

これは誤り。**Workers Free プランでは本アプリの収集ジョブは動作しない。**
律速は D1 ではなく **Workers の CPU 時間**だった。ADR-0003 に訂正を追記済み。

判断: **アーキテクチャ（Workers + D1 + Cron Triggers）は維持する。ADR-0003 を supersede しない。**
ただし **Workers Paid プラン（$5/月）を前提条件として明示する。**

## 1. 実測: GitHub API レスポンスのサイズ

`ymiyamoto63/four-keys-metrics-viewer` に対する実測（2026-09-20、REST API v3）。

| データ | 生レスポンス | 必要な項目のみ | 削減率 |
| --- | ---: | ---: | ---: |
| コミット 1 件 | 5,214 B | 500 B | 10.4x |
| PR 1 件 | 21,140 B | 378 B | 55.9x |
| compare 1 コール（コミット 10 件分） | 349,851 B | 440 B（SHA 列のみ） | **795x** |

**compare API のペイロードの 99.87% はファイル差分で、本アプリでは一切使わない。**

## 2. 確認: Cloudflare の制限（公式ドキュメント、2026-09-20 時点）

### D1

| 項目 | Workers Free | Workers Paid |
| --- | --- | --- |
| 1 データベースの最大サイズ | **500 MB** | **10 GB** |
| アカウント合計ストレージ | 5 GB | 1 TB |
| 書き込み行数 | **100,000 / 日** | 50,000,000 / 月（以降 $1.00 / 100万行） |
| 読み取り行数 | 5,000,000 / 日 | 250億 / 月 |

- **インデックスは書き込み行数を増やす。** インデックス列を含む書き込みでは「テーブルへ 1 行 + インデックスへ 1 行」が計上される
- 行のサイズは行数のカウントに影響しない（1 KB の行も 100 KB の行も 1 行）
- **2026-09-01 以降、無料枠の 1 日あたり制限は実際にクエリを失敗させる**（以前は警告のみ）

### Workers

| 項目 | Workers Free | Workers Paid |
| --- | --- | --- |
| **Cron Trigger あたりの CPU 時間** | **10 ms** | **30 秒**（1 時間未満の間隔）/ **15 分**（1 時間以上の間隔） |
| 外部サブリクエスト / 起動 | **50** | 10,000（最大 1,000万まで設定可） |
| メモリ | 128 MB | 128 MB |
| リクエスト | 100,000 / 日 | 無制限 |

## 3. 見積もり

対象アカウントの実リポジトリの活動量（デフォルトブランチのコミット数、90 日で 1〜86 件）を
もとに、1 スコープ・1 年あたりを 4 シナリオで算出。
PR 数はコミット数の 1/8、デプロイ数は `merge_only` 前提で PR 数と同等とした。
書き込み行数はインデックス 2 本を想定して 3 倍で計上。

| シナリオ | commit | PR | deploy | 行数 | 書込行 | 生 raw 保存時 | 必要項目のみ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 小（life-design-app 相当） | 4 | 1 | 1 | 7 | 21 | 0.4 MB | 0.00 MB |
| 中（gh-dev-pipeline 相当） | 154 | 19 | 19 | 211 | 633 | 7.9 MB | 0.10 MB |
| 大（継続的に活発） | 1,000 | 125 | 125 | 1,375 | 4,125 | 51.6 MB | 0.63 MB |
| 特大（like-chatgpt のバーストが通年続く） | 3,100 | 388 | 388 | 4,264 | 12,792 | 160.2 MB | 1.94 MB |

### 10 スコープ（特大 2 + 大 3 + 中 5）を 1 年分バックフィルした場合

| | 値 | 制限に対して |
| --- | ---: | --- |
| 総行数 | 13,708 | 上限なし |
| 書き込み行数 | 41,124 | 無料枠 100,000 行/日 の **41%**。1 日で完走する |
| ストレージ（生 raw 保存） | **514 MB** | Free の DB 上限 500 MB を**超過**。Paid の 10 GB なら 5.1% |
| ストレージ（必要項目のみ） | **6.3 MB** | Paid の 10 GB の **0.06%** |

### 定常運用（cron 1 時間間隔・10 スコープ）

- 新規イベント 約 34 件/日 → 書き込み **113 行/日**
- Worker 起動 24 回/日

いずれも制限に対して無視できる水準。

## 4. なぜ Workers Free では動かないのか

**Cron Trigger あたりの CPU 時間が 10 ms しかない。**

Cloudflare 公式ドキュメントは「認証、サーバーサイドレンダリング、**大きなペイロードのパース**を
行う重いワークロードは通常 10〜20 ms を使う」と記している。本アプリの収集ジョブは
**342 KB の compare レスポンスを JSON パースする**のが中心的な処理であり、
1 コール分のパースだけで 10 ms を使い切る。分割ジョブにしても解決しない
（1 起動あたりの CPU 上限であり、総量の問題ではないため）。

副次的に、外部サブリクエストが 50/起動に制限される点、
および生 raw 保存時に DB 上限 500 MB を超過する点も Free では障害になる。

**Workers Paid では、1 時間以上の間隔の Cron Trigger に 15 分の CPU 時間が与えられる。**
これは必要量を大きく上回る。

## 5. 設計へのフィードバック

### ADR-0003 への訂正（実施済み）

「無料枠で常時稼働できる」という記述は誤り。**Workers Paid を前提条件とする**旨を追記した。

### cron 間隔 1 時間の選択が追加の理由で裏付けられた

Workers Paid の Cron Trigger の CPU 時間は **1 時間以上の間隔なら 15 分、1 時間未満なら 30 秒**。
ADR-0003 は「週次粒度の指標に分単位の鮮度は不要」という理由で 1 時間間隔を選んだが、
**間隔を 1 時間未満に短縮すると CPU 予算が 30 分の 1 になる**ことが判明した。
1 時間間隔は維持すべきであり、短縮を検討する際はこの制約を思い出すこと。

### `raw` カラムの方針を具体化する必要がある（#8 / #15 へ）

ADR-0002 は「生レスポンスの**必要部分**を `raw` JSON として残す」と書いたが、
「必要部分」の線引きが未定義だった。実測の結果、この線引きは 10〜800 倍の差を生む。

- **compare API のレスポンスを raw として保存してはならない。** 必要なのは SHA 列（0.13%）のみ
- PR の raw を丸ごと保存すると 1 件 21 KB。保存する項目を明示的に列挙すること
- 生 raw 保存でも Paid の 10 GB には遠く届かないため、**容量のためではなく、
  クエリ性能と可読性のために絞る**という位置づけ

## 6. この見積もりの限界

- 活動量はサンプル 4 リポジトリからの外挿であり、実際の利用パターンで変わる
- インデックス数を 2 本と仮定した。#8 のスキーマ確定後に再計算が必要
- D1 の書き込みレイテンシ（1 回の `INSERT` が数ミリ秒かかりうる）は CPU 時間には計上されないが、
  Cron Trigger の実時間には影響する。実測は #23 の E2E で行う
