# ADR-0005: スコープを抽象として持ち、設定はリポジトリ内の設定ファイルで管理する

- ステータス: Accepted
- 日付: 2026-09-20

## 文脈

DORA は指標を「1 つのアプリケーションまたはサービス単位」で適用することを推奨し、
`README.md` も「リポジトリ（あるいはリポジトリ内のサービス単位）をスコープの基本単位とし、
組織横断での安易な合算・比較は行わない」と明言している。

また柱 4 により、「何をデプロイとみなすか」（ADR-0001 のデプロイ検出ルール）は
**設定可能**でなければならない。その設定をどこに置くかを決める必要がある。

## 決定

1. **複数リポジトリを登録し、画面で 1 つずつ切り替えて表示する。合算しない。横並び比較もしない。**
2. 指標の計算対象は「リポジトリ」ではなく **「スコープ」という抽象**として持つ。
   現時点では 1 スコープ = 1 リポジトリだが、将来リポジトリ内をサービス単位に分割できる余地を残す。
3. **スコープ設定はリポジトリ内の設定ファイル**（例 `scopes.toml`）で管理し、
   アプリのデプロイに同梱する。変更には PR とデプロイを要する。
4. **MVP では設定編集 UI を作らない。**

スコープが持つ項目: 対象リポジトリ（owner / repo）、デプロイ検出ルール 1 つ（ADR-0001）、
バックフィル範囲（既定 1 年、ADR-0003）。

## 理由

**合算しない**: `README.md` のアンチパターン「チーム間の競争を煽らない」「個人の評価に使わせない」
に直結する。比較の軸は「他チーム」ではなく「過去の自分たち」に置く。

**スコープという抽象を最初から入れる**: 「リポジトリ」で直接モデリングすると、
サービス単位への分割が必要になった時点で全クエリとスキーマに波及する。
抽象を 1 段挟むコストは今なら小さい。

**設定ファイルにする（編集 UI にしない）**: 理由は運用の楽さではなく**柱 4 の含意**である。
「何をデプロイとみなすか」はチームが議論して合意すべき定義であって、
こっそり画面から書き換えられてよいものではない。設定ファイルなら変更が PR に現れ、
**「この時点で定義を変えた」という履歴が残る**。指標が不連続に跳ねたときに原因を辿れるのは、
この履歴があるからである。編集 UI はその履歴を消す。
スコープ数が 1 桁である以上、再デプロイの手間は論点にならない。

## 検討した代替案

- **D1 のテーブル + 画面から編集**: 即時反映で運用は楽だが、定義変更の履歴が残らない。
  UI 実装コストも増える。却下。
- **設定ファイルを正とし起動時に D1 へ同期**: 履歴は残るが、二重管理と同期タイミングの問題を
  持ち込む。スコープ数が 1 桁の現状では利点がない。却下。
- **1 リポジトリ固定（設定で指定、乗り換えは設定変更）**: 実質すぐ足りなくなる。却下。
- **リポジトリ内をサービス単位に分割できるようにする**: 「何がサービス境界か」の定義が必要で、
  コンセプトの複雑度を一段上げる。抽象だけ用意して実装は後回し。

## 結果・影響

- デプロイ検出ルールの変更は PR として記録される。ADR-0002 の ③ キャッシュ破棄は
  デプロイ時に実行される必要がある。
- 対象リポジトリを増やすたびにデプロイが要る。スコープ数が 2 桁に乗ったら再検討する。
