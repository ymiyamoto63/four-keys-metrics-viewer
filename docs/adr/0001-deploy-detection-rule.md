# ADR-0001: デプロイ検出ルールをスコープごとの設定とし、MVP では 2 戦略に絞る

- ステータス: Accepted
- 日付: 2026-09-20

## 文脈

Four Keys / DORA の 5 指標はすべて「デプロイとは何か」の定義の上に乗っている。
GitHub から取れる候補は複数ある。

- Deployments API の `deployment_status = success`（`environment = production`）
- GitHub Releases の publish
- デフォルトブランチへの merge / push
- 特定の Actions ワークフローの成功実行
- semver タグの push

`README.md` の基本コンセプト 4 は「何をデプロイとみなすか、何を障害とみなすかは組織ごとに異なる。
指標の定義とマッピングルールを設定可能にし、画面上でも辿れるようにする」と明言している。
つまり**単一の定義に決め打ちする設計はコンセプトと矛盾する**。

加えて、最初の利用者となる対象アカウントの直近 active な 4 リポジトリを調査した結果:

| シグナル | 4 リポジトリすべて |
| --- | --- |
| Releases | 0 |
| タグ（semver 含む） | 0 |
| デプロイ名のワークフロー | 0 |
| ワークフロー総数 | 1（生成物の整合性チェック。CD ではない） |
| デフォルトブランチのコミット（90 日） | 38 / 86 / 1 / 2 |
| Deployments API | 確認手段が無く**未検証** |

つまり現時点で確実にデータが存在するのは「デフォルトブランチへのコミット」だけだった。

## 決定

1. **デプロイ検出ルールをスコープごとの設定項目として持つ。** 1 スコープにつき **1 ルールのみ**。
   複数ルールの OR 合成は行わない。
2. **MVP で実装するルールは 2 つ。**
   - `default_branch` — デフォルトブランチへの反映。粒度を設定で選ぶ。
     - `merge_only`（**既定**）: merge commit のみを 1 デプロイとみなす
     - `all_pushes`: デフォルトブランチへの全コミットを 1 デプロイとみなす
   - `workflow_run` — 指定した Actions ワークフローの成功実行を 1 デプロイとみなす
3. **`deployments_api` は保留する。** 後から追加できる抽象は持つが、MVP では実装しない。
4. **`default_branch` ルールのデプロイ時刻は、マージコミット（または対象コミット）の
   committer date を採用する。** PR の `merged_at` は使わない。
5. `default_branch` ルールが有効な間、画面に
   「このスコープは『デフォルトブランチへの merge＝デプロイ』として計算しています」を常時表示する。

## 理由

**1 ルールのみ・OR 合成禁止**: 同一のデプロイが Deployments API とワークフロー成功の両方で
記録されると二重計上が起きる。さらに悪いことに、画面から「どちらで数えたのか」を辿れなくなり、
`README.md` 柱 4（算出ロジックの開示）が破綻する。重複排除ロジックは MVP に入れる価値のない複雑さ。

**既定を `merge_only` にする**: `all_pushes` を既定にすると、調査対象の `like-chatgpt`
（10 日間に 86 コミット）のようなリポジトリで「10 日で 86 デプロイ」という無意味な数字が出る。
さらに ADR-0004 のリードタイムは「コミットした瞬間にデプロイ」となりほぼ全件ゼロになり、
指標が定義によって死ぬ。データ点が少ないほうが、嘘の点が多いより誠実である
（データ不足週の扱いは ADR-0004 を参照）。

**`all_pushes` も残す**: trunk-based で直接 push しつつ自動デプロイする構成は実在し、
そこでは `all_pushes` が正しい。これは柱 4 の「定義は組織ごとに異なる」そのもの。

**`deployments_api` を落とす**: 上記調査で痕跡が確認できず、Workers へのデプロイも既定では
GitHub Deployments を生成しない。検証すらできていない戦略を投機的に実装するより、
`workflow_run` を実装するほうが投資対効果が高い。なお `workflow_run` も現時点でデータは無いが、
CD を導入した瞬間に最も正確な戦略になり、かつ「デプロイを計測可能にするには CD を作ればよい」
という改善の導線そのものになるため残す。

**デプロイ時刻に committer date を使う（`merged_at` ではなく）**: 理由は 2 つ。

1. **検証可能性。** GitHub のタイムスタンプには、過去日付で作れるものと作れないものがある。

   | データ | 過去日付で作れるか |
   | --- | --- |
   | コミット / マージコミットの committer date | **作れる**（git オブジェクトの一部） |
   | PR の `created_at` / `merged_at` | 作れない（GitHub がサーバー時刻で刻む） |
   | Actions の実行日時 | 作れない |
   | Deployments / Releases の日時 | 作れない |

   `merged_at` を採用すると、サンプルリポジトリに 1 年分の履歴を合成できず、
   「週次の推移」（ADR-0004）と「既定 1 年のバックフィル」（ADR-0003）を**そもそも検証できない**。

2. **直接 push への対応。** `merged_at` は PR が存在しないと得られない。committer date なら
   `merge_only` / `all_pushes` の両粒度で同じコードパスが使える。

実リポジトリでは両者はほぼ一致するため、精度上の犠牲はない。

## 検討した代替案

- **単一の固定ルールにする**: 実装は最も軽いが、`README.md` 柱 4 と正面から矛盾する。却下。
- **`all_pushes` を既定にする**: 全リポジトリで必ず線が引けるが、初回起動時に最も壊れた数字を
  見せることになる。却下。
- **複数ルールを OR 合成して「取れるものは全部デプロイ」とする**: 二重計上と説明不能性。却下。
- **Releases / タグ起点のルールを実装する**: 実質「タグ起点」の一種で、`workflow_run` があれば
  大半が代替できる。調査でも 0 件だった。保留。

## 結果・影響

- スコープ設定に `deploy_rule` が必須項目として入る（ADR-0005）。
- デプロイ検出ルールを変更すると過去の指標がすべて変わるため、ルール由来の導出キャッシュは
  破棄する必要がある（ADR-0002）。
- `deployments_api` の実態は**未検証のまま残る**。別途 spike として追跡する。
- 対象アカウントの既存リポジトリには依然として測定対象が乏しいため、検証用のサンプルリポジトリを
  新規に作る（ADR-0003 / ADR-0004 の検証方針）。
