# ADR-0006: アクセス制御をアプリ外に出し、GitHub 認証は単一の read-only PAT で行う

- ステータス: Accepted（2026-09-20 に改訂。下部「改訂」を参照）
- 日付: 2026-09-20

## 文脈

ADR-0003 で自ホスト Web アプリとして Cloudflare Workers に載せることが決まっている。
決めるべきは独立した 2 つの事柄:

1. **誰が画面を見られるか**（画面側のアクセス制御）
2. **アプリが GitHub をどう認証するか**（データ取得側の credential）

利用者は少人数。調査の結果、対象アカウントには **Organization が存在せず、全 37 リポジトリが
個人アカウント所有**であることが分かっている。対象リポジトリには private も含まれる。

## 決定

1. **画面側の認証をアプリ内に実装しない。** アクセス制御はインフラ層
   （Cloudflare Access / リバースプロキシ / VPN）に出す。
2. **GitHub 認証は単一の credential を環境変数（Workers Secrets）で持つ。**
   閲覧者ごとの OAuth トークンは使わない。
3. credential は **fine-grained PAT（read-only、対象リポジトリのみ選択）** とする。
   GitHub App へ移行できる形で実装する。

## 理由

**単一 credential が構造的に要請される**: ADR-0002 で定期収集を選んだ以上、
収集は「閲覧者が誰もいない時間」にも動く必要がある。閲覧者の OAuth トークンでは収集できない。

**画面側の認証をアプリに持たせない**: GitHub OAuth ログインを実装し
「対象リポジトリへの read 権限がある人だけ見られる」を実現しようとすると、
アプリが権限計算を背負うことになる。少人数の自ホスト構成には過剰。
Cloudflare Access が ADR-0003 で選んだ基盤上に無料枠で存在し、自前実装が一切不要。

これは「アクセス制御をしない」という意味ではなく、**アクセス制御をアプリの外に追い出す**判断である。

**GitHub App ではなく fine-grained PAT を選ぶ**: 当初は GitHub App を推した
（レート制限枠が広く、個人に紐づかず、権限を read-only に絞れる）。
しかし調査で **Organization が存在せず全リポジトリが個人所有**であることが分かり、
個人アカウント相手では GitHub App のセットアップ手間に対する見返りが薄い。
fine-grained PAT なら read-only かつ対象リポジトリを明示的に選択でき、
必要な権限の絞り込みはほぼ同等に達成できる。

GitHub App への移行余地は残す。利用が組織に広がる、レート制限が問題になる、
あるいは PAT の期限管理が負担になった時点で再検討する。

## 検討した代替案

- **GitHub OAuth ログインを画面に実装する**: チーム外への URL 漏洩を許容できない場合の選択肢。
  今回はインフラ層で足りると判断したが、要件が変われば最初に見直す箇所。
- **閲覧者ごとの OAuth トークンで GitHub を叩く**: 定期収集と両立しない。却下。
- **GitHub App を単一 credential として使う**: 上記理由で当面見送り。移行先として残す。
- **classic PAT**: 権限の絞り込みが粗い。却下。

## 結果・影響

- **PAT の保管場所（Workers Secrets）と更新運用は未整備。** 期限切れで収集が静かに止まる
  リスクがあるため、ADR-0003 の「最終収集成功時刻の画面表示」がその検知手段を兼ねる。
- **Cloudflare Access の具体的な設定手順は未整備。** これを怠ると URL を知る全員が閲覧できる状態に
  なるため、デプロイ手順に必須ステップとして含める必要がある。
- private リポジトリを対象にする以上、PAT の権限設定ミスは収集失敗として現れる。
  スコープ単位の失敗分離（ADR-0003）により他スコープには波及しない。

## 改訂 (2026-09-20): 自ホスト・ローカル実行への切り替えに伴う変更

ADR-0007 により実行環境が Cloudflare Workers から
「開発マシン上の Docker コンテナ、必要時に起動」へ変わった。
本 ADR の決定のうち 2 つが影響を受ける。

### 決定 1（画面側の認証をアプリ外に出す）→ 前提が消え、より単純に解決した

当初の理由は「Cloudflare Access が ADR-0003 で選んだ基盤上に無料枠で存在し、
自前実装が一切不要」だった。ADR-0007 により Cloudflare Access は使えなくなる。

しかし同時に、**アクセス制御の必要そのものが小さくなった。**
ADR-0007 の決定 3 により、アプリは開発マシン上でのみ、必要なときにだけ動く。
外部からアクセスする者が存在しない。

**改訂後の決定: HTTP サーバーを `127.0.0.1` にバインドする。それ以外のアクセス制御を実装しない。**

Cloudflare Access も、Tailscale も、リバースプロキシも、VPN も不要。
ただし **`0.0.0.0` にバインドしてはならない** — 同一ネットワーク上の他の端末から
認証なしで閲覧可能になり、private リポジトリの活動履歴が漏れる。

「アクセス制御をアプリの外に追い出す」という元の判断は維持されている。
外が Cloudflare Access から OS のネットワークスタックに変わっただけである。

### 決定 2・3（GitHub 認証は単一の fine-grained PAT）→ 維持。保管場所のみ変更

read-only の fine-grained PAT を単一 credential として使う判断は変わらない。
定期収集が閲覧者のトークンでは行えないという理由は、実行環境に依存しない。

**保管場所を Workers Secrets から、環境変数 / `.env` ファイル（Docker コンテナへ注入）に変更する。**

これに伴う注意:

- **`.env` を誤ってコミットしないこと。** `.gitignore` に含める
- Workers Secrets と違い、`.env` は平文でディスク上に残る。開発マシン上のファイルなので
  許容するが、権限の絞り込み（read-only、対象リポジトリのみ）はより重要になる
- PAT の期限切れで収集が静かに止まるリスクは変わらない。
  ADR-0007 が引き継いだ「最終収集成功時刻の画面表示」が検知手段を兼ねる

### 将来ホスティングする場合

ADR-0007 の決定 7 のとおり、チーム共有の道は閉じていない。
その場合は本改訂の決定 1 が再び無効になり、当初の選択肢
（Cloudflare Access / リバースプロキシ / VPN / アプリ内の GitHub OAuth ログイン）に戻る。
`127.0.0.1` バインドを外す変更は、**必ずアクセス制御の導入とセットで行うこと。**

### 実装上の補足 (2026-09-20, #7): コンテナ内のバインド先と、公開範囲を決めている場所

上の「`0.0.0.0` にバインドしてはならない」は、**ホスト上で直接プロセスを動かす場合**の話である。
Docker コンテナ内でこれをそのまま適用すると、アプリが起動しても画面が開かない。

コンテナはネットワーク名前空間が分かれているため、コンテナ内の `127.0.0.1` は
**コンテナ自身**を指す。そこにバインドすると、ポートを公開してもホストから到達できない。

したがって実装は次の形を取る。

| 動かし方 | アプリのバインド先 | 公開範囲を決めているもの |
|---|---|---|
| ホスト上で直接 (`npm start`) | `127.0.0.1`（既定） | アプリのバインド先そのもの |
| Docker コンテナ | `0.0.0.0` | `docker-compose.yml` の `ports: "127.0.0.1:3000:3000"` |

**守るべき不変条件は「アプリが `127.0.0.1` にバインドすること」ではなく、
「このホスト以外から到達できないこと」である。** 後者を満たす箇所が構成によって変わる。

危険なのは、コンテナ用の設定をホスト上での直接実行に持ち込むこと。そのため実装では、
ループバック以外へのバインドを**既定で起動時エラーとし**、`ALLOW_NON_LOOPBACK_BIND=1` の
明示的な指定を要求する（`src/config.ts`）。この指定は `docker-compose.yml` だけが持つ。

`docker-compose.yml` の `ports` 左辺の `127.0.0.1:` を落とすと、その瞬間に
同一ネットワーク上の全端末へ公開される。**この 1 行が唯一の防壁である。**
