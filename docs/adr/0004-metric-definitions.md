# ADR-0004: 指標の算出定義と、その検証方法

- ステータス: Accepted
- 日付: 2026-09-20

## 文脈

MVP で扱うのは**スループット側 2 指標**（デプロイ頻度・変更のリードタイム）。
不安定性側 3 指標は「何を障害とみなすか」という人間の定義に依存し、ラベル運用などの前提を
利用者に強いるため、MVP から外す（`README.md` 柱 1 の軽量性を優先）。

デプロイの定義は ADR-0001 で決まっている。ここで決めるのは、そこから指標をどう出すか。

## 決定

### 変更のリードタイム

- **起点** = そのコミットの **committer date**（author date は使わない）
- **終点** = そのコミットが含まれた**デプロイ**の**デプロイ時刻**（ADR-0001）
- **1 サンプル = 1 コミット。** デプロイ間の差分コミット集合を対象とし、
  コミット 1 件ごとにリードタイムを出す。PR 単位にはしない。
- デプロイ間の差分は **GitHub compare API**
  (`GET /repos/{owner}/{repo}/compare/{base}...{head}`) でグラフ正確に取得する。
  結果は ADR-0002 の**③ キャッシュ**として保存し、デプロイ検出ルール変更時に破棄する。
- 詳細画面に **「コミット → PR open」「PR open → merge」「merge → デプロイ」の 3 区間内訳**を出す。

### デプロイ頻度

- **「週あたり回数」を主指標**、**「デプロイ間隔の中央値」を副指標**として併記する。

### 集計の共通ルール

- **週次バケット、JST 月曜始まり。**
- 代表値は**中央値を主線**とし、**p75 / p90 を薄く重ねる**。平均は使わない。
- **データ点が少ない週は値を出さず、線も繋がない。**

### 検証方法

- 指標計算を**純粋関数に切り出し、記録した GitHub API レスポンス（fixture）でユニットテストする。**
- **サンプルリポジトリ**（`four-keys-sample-service` 相当）を新規に作り、
  **最小アプリ + 本物の CD ワークフロー + 1 年分の合成コミット / マージコミット**を持たせる。
  用途は **E2E（API レスポンス形の確認）に限定**する。

## 理由

**committer date を起点にする**: rebase / cherry-pick / 古いパッチの適用で author date は
数ヶ月前を指すことがあり、リードタイムが実態の何倍にも跳ねる。committer date は
「この履歴に入った時刻」を指すので歪みが小さい。

**PR 単位でなくコミット単位**: PR を経由しない直接 push を取りこぼす。調査した実リポジトリでは
直接 push の比率が高く、PR 単位だとデータの大半が消える。

**compare API を使い、時刻順近似を採らない**: 時刻順近似（デフォルトブランチのコミットを
committer date でソートし「前回デプロイ時刻 〜 今回デプロイ時刻」の窓に割り当てる方法）には
致命的な欠陥がある。**3 週間前に作られた feature branch が今日 merge された場合、
そのコミットの committer date は 3 週間前を指すので時間窓に入らず、集計から丸ごと消える。**
つまりこの近似は、リードタイムが最も長かったコミット＝最も会話の価値があるデータを
システマティックに削り落とす。精度の問題ではなく、**指標が逆向きに嘘をつく**
（放置された PR ほど数値に現れない）問題である。API コストは、稼働中のスコープが数件・
1 時間ポーリングという条件では無視できる。

**3 区間内訳を出す**: 柱 4（算出ロジックの開示）を満たすと同時に、
「遅いのはコーディングか、レビュー待ちか、デプロイ待ちか」という改善の会話に直結する分解になる。
合計値だけでは会話が生まれない。

**中央値 + p75/p90**: リードタイムは右に長い裾を引く分布で、平均は外れ値 1 件で跳ねる。
一方で中央値だけだと「たまに 3 週間かかる PR がある」という一番会話すべき事実が消える。
`README.md` の「会話のきっかけ」という立場では外れ値こそが話の種になる。

**JST 月曜始まり**: 利用者が日本チームであり、UTC 週境界だと月曜午前のデプロイが前週に落ちて
直感に反する。

**日次でも月次でもなく週次**: 少人数チームでは日次はスカスカでノイズだらけ、
月次は施策前後の変化が見えるまで遅すぎる。

**データ不足週を繋がない**: 少数サンプルの中央値を折れ線で繋ぐと嘘をつく。
なお ADR-0001 で `merge_only` を既定にした結果、**これは例外処理ではなく通常の表示状態になる**。

**fixture によるユニットテストを主、サンプルリポジトリを従にする**: 指標計算のバグが出る場所と、
サンプルリポジトリで再現できる場所がズレている。実際に壊れるのは
**週バケットの境界・タイムゾーン・デプロイ 0 件の週・同一時刻の複数デプロイ・
バックフィル途中でのカーソル再開**といった境界条件で、これらをサンプルリポジトリ上で
意図的に発生させるのは不可能か極めて手間。逆に E2E でしか分からないのは
「GitHub API のレスポンス形が想定どおりか」だけ。

**サンプルリポジトリが合成履歴と本物の CD の両方を持つ理由**: ADR-0001 に示したとおり、
過去日付で作れるのはコミット / マージコミットのみで、Actions の実行日時は作れない。
したがって**合成履歴だけでは `workflow_run` ルールを検証できず、
本物の CD だけでは 1 年分の推移を検証できない**。片方では MVP の 2 戦略の半分しか検証できない。

## 検討した代替案

- **起点を PR の open 日時にする**: レビュー待ち時間だけを測ることになり、
  DORA の定義（コミットからデプロイまで）から外れる。3 区間内訳の一部として出すに留める。
- **起点を PR の merge 日時にする**: デプロイ待ち時間だけになる。同上。
- **時刻順近似でコミットを割り当てる**: 上記理由で却下。
- **平均値を主指標にする**: 外れ値に弱い。却下。
- **単一スコアに丸める / 目標値を提示する**: `README.md` が明示的に避けるとしたアンチパターン。却下。

## 結果・影響

- チャートライブラリは「欠損週を勝手に補間しない」ことが選定条件になる。
  多くのライブラリは既定で補間するため、実装時の要注意ポイントとして残る。
- 合成履歴の具体設計（何週分・週あたり何コミット・PR 何件・リードタイムの分布）は未着手。
  ここを雑に作ると「常に綺麗な線が出るテストデータ」になり、欠損週や外れ値の表示を検証できない。
- 不安定性側 3 指標と Quick Check セルフ評価は MVP に入れない。
  Quick Check の価値は自動算出値との突き合わせ（柱 5）にあるが、
  MVP では**突き合わせる相手が存在しない**ため、単独で入れると
  「アンケートに答えて点が出るだけ」の機能になり、避けると宣言した「単一スコアに丸める」に近づく。
  不安定性側 3 指標を載せる段階で同時に入れる。
