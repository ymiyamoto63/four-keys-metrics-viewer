# ADR-0003: Cloudflare Workers + D1 + Cron Triggers に載せ、収集は再開可能な分割ジョブにする

- ステータス: Accepted（2026-09-20 に訂正を追記。下部「追記」を参照）
- 日付: 2026-09-20

## 文脈

ADR-0002 で「常時動く定期収集ジョブ + イベントストア」が確定した。
ADR-0006 で「アプリ内に認証を持たず、アクセス制御はインフラ層に出す」が確定した。
したがって要件は「cron が動く / DB がある / 常時稼働する / 運用が軽い / アクセス制御を外に出せる」。

利用者は少人数、スコープ数は 1 桁の想定。

## 決定

1. **Cloudflare Workers + D1 + Cron Triggers + Workers Static Assets** に載せる。
   フロントも同じ Worker に同居させ、1 デプロイに閉じる。
2. フロントエンドは **Hono + JSX のサーバーサイドレンダリング**。チャートのみクライアント JS。
   SPA にしない。
3. 画面は **2 階層**。サマリ（選択中スコープの全指標）→ 指標詳細（チャート + 根拠イベント一覧）。
   個別イベントの詳細は自前で持たず、GitHub の該当 PR / コミットへ外部リンクする。
4. **収集トリガはポーリングのみ。cron 間隔は 1 時間。** webhook は使わない。
5. **初回バックフィルは既定 1 年**（スコープごとに設定可能）。
   **収集カーソルを DB に持つ再開可能な分割ジョブ**として実装し、cron の各周回で少しずつ遡る。
6. 失敗は**スコープ単位で独立**させ、1 スコープの失敗が他を止めないようにする。
7. **レート制限に到達したら待機せず即座に中断**し、次の cron 周回に委ねる。
8. 各スコープの**最終収集成功時刻**と**バックフィル進捗**を画面に常時表示する。

## 理由

**Workers を選ぶ**: 定期収集は「誰も見ていない時間に動く」ことが必須で、VPS 構成ではそのためだけに
サーバーを維持し続けることになる。Cron Triggers と D1 が標準装備で、サーバー管理なしに常時稼働でき、
ADR-0006 で外出しすると決めたアクセス制御の受け皿（Cloudflare Access）も同じ基盤上にある。
既存の `cloudflare-learning` リポジトリがあり、学習投資も既にある。

**SPA にしない**: 画面が 2 階層しかなく、必要な相互作用は「チャートの点をクリック → 根拠イベント一覧」
だけで、これはリンク遷移で成立する。SPA が持ち込むルーティングと状態管理に見合う要件がない。

**webhook を使わない**: ADR-0004 で集計粒度を**週次**に決めた以上、分単位の鮮度に価値がない。
webhook は公開エンドポイント・署名検証・再送/重複処理を抱えるうえ、
「webhook 設定より前の履歴は取れない」ためバックフィル用のポーリングを結局消せない。
取得経路が 2 つになることは、ADR-0001 の「二重計上を避ける」方針とも相性が悪い。

**バックフィルを分割ジョブにする**: Workers には CPU 実行時間の上限があり、
**一括取得は必ず途中で死ぬ**。収集カーソルを持てば中断しても損失がなく、
「過去に遡る収集」と「最新を追う収集」を同じ仕組みで書ける。

**既定 1 年**: 週次バケットで推移を見るには数十週分が要る。90 日では週 13 本しか点が打てず
「推移」にならない。全履歴は、1 年以上放置されたリポジトリ群を考えると API 消費の無駄が大きい。

**レート制限時に待機しない**: Workers の実行時間上限下で `sleep` は自殺行為。カーソルがあるので
中断してよい。

**収集状態を画面に出す**: ADR-0004 で「データ不足の週は値を出さない」と決めたが、
**収集が壊れている期間と、本当にデプロイが無かった期間は画面上で同じ空白に見える**。
最終収集成功時刻を出さないと利用者は空白を「デプロイしていない」と誤読する。
これは表示の親切さではなく**指標の正しさの一部**である。

## 検討した代替案

- **Node/TypeScript 単一プロセス + SQLite を Docker で VPS/自宅**: ベンダーロックがなく
  ローカルと本番が同一になるが、サーバーの面倒を見続ける必要がある。
  Workers の CPU 時間上限や D1 の制約を受け入れられない場合の退避先として記録しておく。
- **Next.js on Vercel + Postgres (Neon/Supabase)**: エコシステムは厚いが、
  cron・DB・ホスティングが 3 ベンダーに分かれる。却下。
- **React SPA + Recharts**: 2 画面には過剰。却下。
- **webhook 併用**: 上記理由で却下。

## 結果・影響

- **既知のリスク**: D1 は SQLite ベースで書き込みスループットと DB サイズに制約があり、
  Workers には CPU 実行時間の上限がある。分割ジョブ設計はこの制約への直接の対応だが、
  容量の実見積もりは未実施（ADR-0002 の積み残し）。
- PAT は Workers Secrets に置く（ADR-0006）。保管と更新の運用手順は未整備。
- Cloudflare Access の具体設定手順は未整備。
- チャートライブラリは未選定。ADR-0004 の「欠損週を補間しない」が選定条件になる。

## 追記 (2026-09-20): 無料枠では動作しない — Workers Paid を前提条件とする

本 ADR は当初「**無料枠で常時稼働でき**」と記していたが、これは**誤りだった**。
#25 の見積もりで判明した事実に基づき訂正する。該当箇所の記述は修正済み。

### 事実

| 項目 | Workers Free | Workers Paid |
| --- | --- | --- |
| **Cron Trigger あたりの CPU 時間** | **10 ms** | 30 秒（1 時間未満の間隔）/ **15 分**（1 時間以上の間隔） |
| 外部サブリクエスト / 起動 | 50 | 10,000 |
| D1 の 1 データベース最大サイズ | 500 MB | 10 GB |

本アプリの収集ジョブの中心的な処理は **342 KB の compare レスポンスの JSON パース**であり
（実測値は `docs/spikes/0025-d1-capacity.md`）、Cloudflare 公式ドキュメントが
「大きなペイロードをパースする重いワークロードは通常 10〜20 ms を使う」と記すとおり、
**1 コール分のパースだけで Free の 10 ms を使い切る**。

これは 1 起動あたりの CPU 上限であり、本 ADR の決定 5（再開可能な分割ジョブ）でも解決しない。

### 訂正後の決定

**アーキテクチャ（Workers + D1 + Cron Triggers）は維持する。
ただし Workers Paid プラン（$5/月）を前提条件とする。**

D1 の容量・書き込み制限そのものは、想定規模に対して一切ボトルネックにならないことが確認された
（10 スコープ・1 年分のバックフィルで書き込み 41,124 行、ストレージ 6.3 MB）。
**律速は D1 ではなく Workers の CPU 時間だった。**

### cron 間隔 1 時間は維持すること

Workers Paid の Cron Trigger の CPU 時間は **1 時間以上の間隔なら 15 分、1 時間未満なら 30 秒**。
決定 4 の 1 時間間隔は当初「週次粒度の指標に分単位の鮮度は不要」という理由で選んだが、
**間隔を 1 時間未満に短縮すると CPU 予算が 30 分の 1 になる**。
短縮を検討する際はこの制約を思い出すこと。

### 退避先について

本 ADR が代替案として記録した「Node + SQLite を Docker で自ホスト」は、
**月 $5 を払うか、サーバーを自分で管理するか**という選択になる。
今回は前者を選ぶ。
