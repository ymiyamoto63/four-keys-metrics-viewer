# ADR-0007: Node + SQLite を Docker で自ホストし、開発マシン上で必要時に起動する

- ステータス: Accepted
- 日付: 2026-09-20
- 関連: **ADR-0003 を supersede する**

## 文脈

ADR-0003 は Cloudflare Workers + D1 + Cron Triggers を選び、その理由の 1 つに
「無料枠で常時稼働できる」ことを挙げていた。

#25 の見積もり（`docs/spikes/0025-d1-capacity.md`）で、この前提が誤りであることが判明した。

- Workers Free の **Cron Trigger あたりの CPU 時間は 10 ms**
- 収集ジョブの中心処理は compare レスポンス（**実測 342 KB**）の JSON パースで、
  1 コール分のパースだけで 10 ms を使い切る
- 1 起動あたりの上限のため、ADR-0003 の分割ジョブ設計でも解決しない
- したがって **Workers Paid（$5/月）が前提条件**になる

D1 の容量・書き込み制限そのものは十分に余裕があった（10 スコープ・1 年分のバックフィルで
書き込み 41,124 行、ストレージ 6.3 MB）。**律速は D1 ではなく Workers の CPU 時間だった。**

この結果を受けて、ADR-0003 が代替案として記録していた
「Node + SQLite を Docker で自ホスト」へ切り替える判断が下された。

## 決定

1. **Node.js + TypeScript の単一プロセス**とし、**Docker コンテナ 1 つ**に収める。
2. ストアは **SQLite**。ドライバは **`better-sqlite3`**。DB ファイルは Docker volume に置く。
3. **開発マシン上で、必要なときに起動する。常時稼働させない。**
4. 定期実行は**アプリ内スケジューラ**（単一プロセス内）。
   **起動時に自動で追いつき、稼働中は 1 時間ごと**に収集する。
5. HTTP サーバーは **`127.0.0.1` にバインド**し、外部に公開しない。
6. **再開可能な分割バックフィルを維持する**（収集カーソルを DB に持つ）。
7. **チーム共有は将来の拡張として設計上の余地を残す。** ただし MVP では提供しない。

### ADR-0003 から引き継ぐ決定（変更なし）

- フロントエンドは **Hono + JSX のサーバーサイドレンダリング**、チャートのみクライアント JS
- 画面は **2 階層**（サマリ → 指標詳細）。個別イベントは GitHub へ外部リンク
- **収集トリガはポーリングのみ。webhook は使わない**
- **初回バックフィルは既定 1 年**（スコープごとに設定可能）
- 失敗は**スコープ単位で独立**させる
- **レート制限に到達したら待機せず即座に中断**し、次のサイクルに委ねる
- 各スコープの**最終収集成功時刻**と**バックフィル進捗**を画面に常時表示する

## 理由

**Node + SQLite にする**: Workers の CPU 時間・サブリクエスト・ペイロードサイズの制限から解放される。
Node には実行時間の上限がなく、342 KB の JSON パースを何回行っても問題にならない。

**コスト削減が理由ではない。** 開発マシン上で動かす限り追加費用はかからないが、
VPS を借りれば Workers Paid と同水準かそれ以上になる。
この切り替えの便益は**実行環境の制限からの解放とベンダーロックの回避**であって、費用ではない。

**`better-sqlite3` を選ぶ**: 同期 API が SQLite の性質に素直で、ADR-0002 の
「指標はクエリ時に毎回計算する」という設計とも相性が良い。
`node:sqlite`（Node 組み込み）も候補だが、Node のバージョン要件と安定度を実装時に
現物で確認する必要があり、MVP では実績を優先する。

**アプリ内スケジューラにする（システム cron / 別コンテナにしない）**: ADR-0003 の
「1 デプロイに閉じる」思想を維持する。別プロセス・別コンテナ構成はコンテナ定義と
配布手順を増やす割に、得られるのはプロセス分離だけ。

**`127.0.0.1` にバインドする**: 決定 3 により外部からアクセスする者がいない。
ADR-0006 が想定していた Cloudflare Access のような仕組みは**不要になった**（ADR-0006 の改訂を参照）。
`0.0.0.0` にバインドすると、同一ネットワーク上の他の端末から認証なしで閲覧可能になる。

**再開可能な分割バックフィルを維持する（理由は差し替え）**: ADR-0003 では
「Workers の CPU 上限下では一括取得が必ず死ぬ」ことが理由だったが、この制約は消えた。
それでも維持するのは、根拠が次に置き換わるため。

- **コンテナの再起動・停止・クラッシュで中断されうる。** 決定 3 により、
  むしろ ADR-0003 の構成より中断頻度が高い
- **GitHub のレート制限（認証済み 5,000 req/hour）は自ホストでも変わらない**
- 決定 4 の「起動時の追いつき」は、長期間起動しなかった場合に大量のデータを遡ることになり、
  分割と再開がそのまま必要になる

## 検討した代替案

- **Workers Paid（$5/月）を払って ADR-0003 を維持する**: 常時稼働が保たれ、
  チーム共有（共有 URL）も成立する。今回は選ばれなかった。
- **VPS で自ホストして常時稼働させる**: 常時稼働とチーム共有は保たれるが、
  費用は Workers Paid と同水準かそれ以上になり、サーバー管理の手間が加わる。
- **自宅サーバー / NAS で常時稼働させる**: 既存のハードウェアがあれば費用はかからない。
  決定 3 を変える場合の最有力候補として記録しておく。

## 結果・影響

### 「チームで共有 URL を見る」という当初の前提は失われた

設計の最初の決定は「少人数チーム向けの自ホスト Web アプリ（共有 URL）」であり、
これは「ローカル実行の CLI / ツール」を退けて選ばれたものだった。
決定 3 により、**実質的には Web UI を持つローカルツールになる。**

コードは変わらない（HTTP サーバーをどこで動かすかの違いだけ）ため、
将来ホスティングする道は閉じない。ただし `README.md` のコンセプト章は
「チームが眺めて会話のきっかけにする」と書いており、現状との乖離を放置すると害になるため、
**現状は単一利用者のローカル実行である旨を注記する。**

### データが古いことが通常状態になる

常時稼働しないため、**最後に起動した時点までしかデータがない**。
1 ヶ月起動しなければ 1 ヶ月分の遅れが溜まる。

これにより、ADR-0003 から引き継いだ「最終収集成功時刻の常時表示」は
**あれば良いものから必須に格上げされる**。これが無いと、利用者は古いデータを
現在の状態として読むことになる。

### その他

- SQLite ファイルは Docker volume に置くため、**volume を消すと全履歴が失われる**。
  バックフィルで復元できるが、既定 1 年より古いデータは戻らない。バックアップ手順が要る
- GitHub の PAT は Workers Secrets ではなく、環境変数 / `.env` ファイルで渡す（ADR-0006 の改訂を参照）
- `docs/spikes/0025-d1-capacity.md` の D1 に関する数値は、この ADR により**適用されなくなった**。
  ただし GitHub API レスポンスの実測値（コミット 5.2 KB / PR 21 KB / compare 342 KB）と、
  それに基づくストレージ見積もりは SQLite でもそのまま有効
