# ADR-0002: 生イベントのみを保存し、指標はクエリ時に計算する

- ステータス: Accepted
- 日付: 2026-09-20

## 文脈

`README.md` の基本コンセプトのうち 2 つがデータ設計を直接拘束する。

- 柱 3「推移を見る（点ではなく線）」— 時系列の履歴が要る
- 柱 4「算出ロジックを開示する」— 集計値だけでなく、**その根拠となった個々のイベントまで辿れる**必要がある

加えて ADR-0001 で「デプロイ検出ルールは設定で変わる」と決めたため、
**同じ生データから異なる指標が出うる**という前提がある。

取得方式には (a) 画面を開くたびに GitHub API を叩いて計算、(b) 定期収集して自前ストアに蓄積、
(c) TTL キャッシュのみ、の選択肢があった。

## 決定

1. **定期収集して自前ストアに蓄積する。** オンデマンド計算は採らない。
2. **保存するのは正規化した生イベントのみ。指標の集計値は一切保存しない。**
   指標はクエリ時に毎回、生イベントから計算する。
3. スキーマは**ハイブリッド**とする。正規化テーブル（`commits` / `pull_requests` / `deploy_events`）
   を持ち、各行に GitHub 生レスポンスの必要部分を `raw` JSON カラムとして残す。
4. 導出データを **3 階層**に分けて扱う。
   - **① 生イベント** — 恒久保存
   - **② 指標の集計値** — 保存しない
   - **③ 外部 API を再取得しないと復元できない導出** — キャッシュとして保存し、
     **スコープのデプロイ検出ルールが変わったら破棄する**
5. 障害イベントのテーブルには、MVP で使わなくても取得元を示す `source` 列を最初から持たせる。

## 理由

**集計値を保存しない**: ADR-0001 でデプロイ検出ルールを可変にした以上、集計値を保存すると
設定変更のたびに全再計算が必要になり、再計算漏れが静かな不整合として残る。
また生イベントを持っていれば柱 4 のドリルダウンがそのまま実現できる。
「5 指標を見据えたデータモデル」は、指標ごとのテーブルではなく
**イベントストア + 解釈レイヤー**の形でこそ素直に拡張できる。

**単一の汎用イベントテーブル（`event_type` + `payload` JSON の 1 枚）にしない**: 柔軟だが、
ADR-0004 で決めた「コミット単位でリードタイムを出し週次中央値を取る」クエリが
JSON 掘りばかりになり、D1（SQLite）上で現実的な速度にならない。型も制約も効かない。

**`raw` JSON を併せ持つ**: 収集時に取り落とした項目が後から必要になったとき、
GitHub を再度叩かずに再構築できる。放置されたリポジトリの過去データは再取得コストが高い。

**③ の階層を明示する理由**: 「集計値は保存しない」という原則だけでは、ADR-0004 の
compare API によるコミット範囲の扱いを誤る。これは集計値ではないが導出であり、かつ
**外部 API を叩き直さないと復元できない**。保存してよいが、ルール変更時に破棄しなければ
古い導出が生き残り、柱 4 の「辿れる」が嘘になる。この但し書きが無いと設計が壊れる。

## 検討した代替案

- **オンデマンド計算（ストアなし）**: 実装は圧倒的に軽く状態も持たないが、毎回レート制限を食い、
  「1 年前からの推移」を出すたびに大量取得が発生する。柱 3 と両立しない。却下。
- **TTL キャッシュのみ**: 上記の緩和にしかならず、履歴の恒久保持にならない。却下。
- **単一の汎用イベントテーブル**: 上記理由で却下。
- **指標の集計値を日次/週次で materialize する**: 高速だが、ルール変更時の再計算と不整合が
  実運用の主要な障害要因になる。却下。

## 結果・影響

- デプロイ検出ルールの変更操作は、③ のキャッシュ破棄を必ず伴う。実装上の不変条件とする。
- 指標計算は生イベントに対する純粋関数として切り出せる。テスト戦略（ADR-0004）はこれに依存する。
- D1 の容量・書き込み制限に対する見積もりは**未実施**。別途 spike として追跡する。
